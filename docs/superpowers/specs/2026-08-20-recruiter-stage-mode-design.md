# 招聘模块 · 面试台模式（方案 A）设计

**日期**：2026-08-20
**取代**：`2026-08-20-recruiter-ui-redesign-design.md`、`2026-08-20-recruiter-answer-capture-design.md` 里的界面部分（数据层与 AI 层不变）

## 诊断

现有实现把三件事塞进同一套骨架（左栏候选人 + 步骤 Tab + 双栏工作台）：

| 场景 | 特点 | 现有骨架为什么不合适 |
|---|---|---|
| 面试**前** | 配置密集，可以慢 | 配置项散在 Tab 和弹窗里 |
| 面试**中** | 双手忙，眼睛在候选人身上，看屏幕时间极短 | 题干、评分标准、答案框分散在三处，要来回扫视；切题靠点列表 |
| 面试**后** | 阅读与决策 | 报告挤在第三个 Tab 里 |

另外两处硬伤：

- **步骤条撒谎**。它长得像向导（编号 + 对勾），但既不强制顺序也不代表进度，实际只是三个视图的 Tab。
- **题目是文件浏览器形态**。「列表 + 详情」适合浏览，而面试是线性推进的——面试官要的是「下一道」，不是「找一道」。

## 方案：模式分离

不再用 Tab 切换视图，而是切换**模式**。三个模式各自是独立路由、独立形态：

```
/recruit                              岗位列表        （基本不变）
/recruit/[jobId]                      候选人列表       （大改：去掉左栏+Tab）
/recruit/[jobId]/c/[id]/prep          准备            （新）
/recruit/[jobId]/c/[id]/stage         面试台 · 全屏    （新）
/recruit/[jobId]/c/[id]/report        复盘            （新）
```

### 岗位列表页

只加一个数：**面试中**。A 引入了「已出题但还没评价」这个中间状态，现在的「候选人 / 已面 / 通过」体现不出来。四个数排一行。

### 候选人列表页（原岗位页）

去掉 `CandidateSidebar` 和 `StepTabs`，改成一张表。每行右侧一个**随状态变化的主按钮**——一行一个动作，不用先进工作台再找 Tab：

| 候选人状态 | 判定依据 | 主按钮 | 去向 |
|---|---|---|---|
| `need_resume` | `resumeText` 为空 | 传简历 | `prep` |
| `need_questions` | 有简历，`questions` 为空 | 生成题目 | `prep` |
| `interviewing` | 有题目，无评价 | 开始面试 / 继续面试 `n/m` | `stage` |
| `done` | 有评价 | 看报告 | `report` |

`n/m` 用已记录答案数，让「继续」有确切含义。

页面其余部分保留：岗位 JD 卡片（可编辑）、搜索、新增/重命名/删除候选人、候选人对比表（≥2 人已评价时出现）。

### 准备页

单列，从上到下：

1. **简历** — 上传解析 或 粘贴文本（复用 `ResumeDropzone` + `ResumePanel`）
2. **考察维度** — 只读展示岗位配置（维度色点 + 名称 + 权重 + 分到几题），右上角「改岗位配置」打开 `JobFormDialog`
3. **底部固定操作条** — 「生成题目」；已有题目时变成「重新生成」+「开始面试」

维度在这里**只读**。候选人级的 `dimensionsOverride` 数据层支持但界面不暴露——从来没人用过，先不加。

### 面试台（核心）

`fixed inset-0 z-50`，盖住顶部导航。不盖的话「专注」是假的——屏幕上还挂着「工作台/模板/面试模拟」，人就还在一个通用页面里。

```
┌──────────────────────────────────────────────────────┐
│ 张三   ▰▰▰▱▱▱▱▱  3/8 · 已用 22 分钟      [结束面试]   │  顶栏
├────────────────────────────────┬─────────────────────┤
│ ● 专业技能  hard  建议 8 分钟   │ 评分标准             │
│                                │  │优秀：…            │
│ 你简历里说用 Golang 重写了      │  │合格：…            │
│ 订单服务，为什么不直接优化      │  │不合格：…          │
│ 原来的 Java 服务？             │                     │
│                                │ 追问                 │
│ ┌────────────────────────────┐ │  · 当时 QPS 多少     │
│ │ 候选人回答                  │ │  · 迁移期怎么双写    │
│ │ 说是 Java 那版 GC 停顿…▌    │ │                     │
│ └────────────────────────────┘ │ 参考答案             │
│                                │  › 展开              │
│ [上一题] [记录并下一题]         │                     │
│         ⌘↵ 下一题  esc 退出     │                     │
└────────────────────────────────┴─────────────────────┘
```

关键决策：

- **题干放大到 21px**，是全页最大的字。面试中抬眼扫一次就要读完。
- **答案框紧贴题干下方**，不再钉在页面底部。现在题干在上、输入框在最下面，中间隔着评分标准和追问，记一句话要上下扫视两次。
- **评分标准/追问/参考答案固定在右栏**，不随滚动跑掉。参考答案默认折叠——先听候选人说。
- **顶部进度带按维度着色**，一眼看出还剩几道、分别是什么类型。可点跳题。
- **键盘**：`⌘↵` 记录并下一题，`⌘←/→` 上下题，`esc` 退出。面试中手在键盘上，不该去找鼠标。
- **随时可退**。答案早就防抖落库了，退出不丢东西。

### 复盘页

现有 `EvaluationPanel` 原样搬过来，加一个返回候选人列表的面包屑。「粘贴整段面试记录」保留在顶部——线下面试、别人代面的场景还需要它，但不再是主路径。

## 数据与 AI 层

**不动**。三张表、维度描述、按维度并发出题、参考答案、逐题答案防抖落库，全部保持现状。这次只改界面与路由。

唯一的数据层改动：`findCandidateStatsByUserId` 多查一个 `status` 字段，供岗位卡片算「面试中」。

## 实现中要小心的坑

这些是上两轮踩过的，写进来免得重犯：

1. **`Textarea` 是 `field-sizing-content`，`rows` 属性无效**。必须用 `min-h-[]` / `max-h-[]`，且一定要给 `max-h`，否则长文本把容器撑到几千像素。
2. **`Card` 是 `flex flex-col`**，直接子元素会拉满宽度。横向布局要显式 `flex-row`，行内小按钮要 `self-start`。
3. **`messages/*.json` 不能用 JSON 序列化回写**，会把 `editor.fields.months` 的数字键重排。只能用文本锚点插入。
4. **`Link`/`useRouter`/`usePathname` 必须从 `@/i18n/routing` 导入**，不是 `next/*`。
5. **`pnpm lint` 基线是 1340 个问题**（几乎全是 `no-explicit-any`）。验收标准是「不新增非 any 违规」，不是清零。
6. **切题时必须先冲刷防抖窗口里未落库的答案**。`key={question.id}` 会让详情组件整体重挂载，指望它自己在卸载时保存是不可靠的——冲刷的责任在父组件的切题回调里。
7. **`dimensionsOverride` 仍要参与出题**：面试台和准备页读维度时，优先候选人覆盖、再退岗位配置，逻辑和现在的 API 一致。

## 验收

- 四条路由都能直达，刷新不丢状态
- 候选人列表的主按钮在四种状态下分别指向正确的页面
- 面试台盖住顶部导航，`esc` 退出回候选人列表
- 面试台里连续记录三道题的答案，刷新后都在
- 岗位卡片的「面试中」数与实际相符
- `pnpm test` 全绿，`tsc --noEmit` 干净，招聘相关文件无新增非 any lint 违规
- 中英两套 messages 键路径一致
