# 招聘面试题蓝图设计

## 背景

招聘模块当前按能力维度并发生成题目。每个请求只知道单个维度及其题数，无法看到最终整场面试的题型组合。因此，即使提示词要求项目题、场景题、八股题和压力面，模型仍可能在每个维度内重复选择相似问法，最终缺少 Go 基础、中间件、数据库等岗位必考内容。

当前生成结果还会把简历中的技术关键词扩写成未经证实的实现事实。例如，简历出现 MQTT 和 ONNX Runtime，不代表候选人一定在同一进程中用 Worker Pool、CGO 或 `runtime.LockOSThread` 处理推理任务。此类题目和参考答案会误导面试官。

## 目标

1. 先规划整场面试的题型与知识覆盖，再生成具体问题。
2. 将题型、能力维度和事实来源作为三个独立维度。
3. 保证 Go 后端岗位覆盖语言基础、并发、数据库、中间件、项目和系统场景。
4. 严格区分简历事实、JD 要求与简历缺口，禁止把推断写成候选人的真实经历。
5. 保留现有短题干、追问阶梯、评分标准、参考答案、危险信号和按维度计分能力。

## 非目标

- 本期不把外部 GitHub 仓库内容复制进产品或建立向量数据库。
- 本期不增加在线检索或运行时访问 GitHub。
- 本期不重做评分模型和报告页面。
- 本期不引入数据库表迁移；题目仍存储在现有 JSON 字段中。

## 核心模型

### 题型

每道题新增 `category`：

```ts
type InterviewQuestionCategory =
  | 'go_fundamentals'
  | 'backend_fundamentals'
  | 'middleware_database'
  | 'project_deep_dive'
  | 'system_scenario'
  | 'communication_pressure'
  | 'hr_motivation';
```

`category` 决定问题以何种方式取证；现有 `dimension` 决定该题计入哪个能力维度。两者不能互相替代。

### 事实来源

每道题新增：

```ts
type InterviewQuestionSource = 'resume' | 'jd' | 'gap';

interface InterviewQuestion {
  source: InterviewQuestionSource;
  evidence: string;
}
```

- `resume`：只能引用简历明确写出的项目、职责、技术和数字。
- `jd`：根据 JD 创建假设场景，题干必须明确是场景，不得暗示候选人做过。
- `gap`：验证 JD 必备项但简历缺少的能力，不得把缺口伪装成项目经历。
- `evidence`：完整复用对应事实清单中的一项，供调试和面试官判断题目是否成立。服务端按 Unicode、大小写和空白归一后做精确成员校验；不接受改写、拼接或只截取其中一段。

老题目读取时使用兼容默认值：`category = project_deep_dive`、`source = resume`、`evidence = ''`。这些默认值仅保证展示与评分兼容，不用于重新解释历史题目的质量。

## 两阶段生成流程

### 第一阶段：生成全局蓝图

新增一次轻量模型请求，输入岗位名称、JD、完整简历、能力维度和总题数，输出：

1. `resumeFacts`：可直接引用的事实，禁止添加原文没有的规模、故障、方案和贡献。
2. `jdRequirements`：岗位必考知识主题。
3. `gaps`：JD 要求但简历未证明的内容。
4. `slots`：数量严格等于岗位题数的题目槽位。

每个槽位包含：

```ts
interface QuestionSlot {
  category: InterviewQuestionCategory;
  source: InterviewQuestionSource;
  dimension: string;
  topic: string;
  evidence: string;
  difficulty: QuestionDifficulty;
}
```

蓝图 schema 使用 Zod 校验。服务端拒绝无效维度、维度题数配额不符以及任何槽位总数偏差；不会校正、截断或用泛化题静默补齐。

每个维度的槽位数由现有 `allocateQuestions` 最大余额法按配置权重确定，与岗位配置界面展示的题数完全一致。蓝图提示词携带每个维度的 key、权重、描述和精确题数，服务端对输出再次校验。

### 蓝图配额

提示词根据岗位动态选择题型，但技术岗位必须满足以下最低覆盖：

- 技术基础类总计至少 30%，包括 Go、后端原理、数据库和中间件。
- 项目深挖约 20% 至 30%。
- 系统/故障场景约 15% 至 25%。
- 沟通、压力和 HR 合计约 15% 至 25%。
- 至少一道 `gap` 题；若 JD 与简历不存在显著缺口，则改为 JD 场景题。

对于非 Go 岗位，蓝图不得生成 `go_fundamentals`。对于 Go 岗位，若总题数不少于 8，至少两道 `go_fundamentals`，且 `middleware_database`、`project_deep_dive`、`system_scenario`、`communication_pressure`、`hr_motivation` 各至少一道。小于 8 题时不强制这组单类别配额，避免与总题数和维度配额冲突。

### 第二阶段：按槽位生成题目

按能力维度对槽位分组并发请求，保留现有并发性能。与当前流程不同，每一路不再自行决定题型，而是必须逐槽位生成：

- 槽位已指定 `category/source/topic/evidence/difficulty`。
- 模型只能生成题干、意图、评分标准、追问、参考答案和危险信号。
- 返回结果按槽位顺序对齐；服务端用槽位值覆盖模型返回的分类、来源、维度和难度，防止模型漂移。
- 每个请求收到全局事实清单和禁止假设清单，从而让不同维度共享同一事实边界。

## 知识主题策略

提示词内置岗位知识域指导，不复制第三方答案。Go 后端岗位的蓝图主题应覆盖：

- Go：GMP、Goroutine/Channel、Context、内存逃逸、GC、Map/Slice/Interface、锁与竞态、pprof/trace。
- API 与网络：HTTP、gRPC、连接管理、超时、重试、幂等、限流。
- 数据库与中间件：MySQL 索引/事务/锁、Redis 一致性与淘汰、MQ 可靠投递/重复消费/积压。
- 分布式与可观测性：CAP 与一致性选择、服务隔离、Metrics/Logs/Tracing、容量和故障治理。

基础题必须遵循“机制 → 可观察现象 → 工程决策”的结构，不能只问术语定义，也不能把某个冷僻实现细节设为唯一正确答案。

## 失败处理

- 蓝图生成或解析失败：返回明确错误，不退回旧的按维度自由生成逻辑，避免用户误以为拿到了高质量题组。
- 某个题目分组生成失败：记录服务端错误；由于最终结果无法与蓝图全部槽位一一对应，整次生成失败且不覆盖旧题。
- 模型返回数量与槽位不一致：整次生成失败；不截断超额题目，也不保存任何不完整结果。
- 重新生成成功前，不清除候选人的旧题目。

## 展示与兼容

- 本期不要求新增筛选 UI。
- 面试台在题目维度标签旁显示题型标签，帮助面试官判断当前轮次覆盖。
- `source/evidence` 暂不默认展示，避免页面过载；保留在数据中供后续“出题依据”抽屉和质量诊断使用。
- 跳过、逐题答案记录、评分过滤逻辑保持不变。
- 评分提示词继续按 `dimension` 计分，但会收到 `category/source/evidence`，用于避免把 JD 假设场景误判成候选人的真实经历。

## 测试

### 单元测试

- 蓝图 schema 接受完整合法结果并拒绝非法分类、来源和槽位数量。
- 蓝图维度数量与岗位配置界面的权重分配一致，且提示词包含维度描述。
- Go 岗位蓝图提示词和验证同时保证足够大面试的必需题型覆盖。
- 每个槽位的 `evidence` 必须是对应 `resumeFacts` / `jdRequirements` / `gaps` 清单的归一化精确成员。
- 槽位按维度正确分组，顺序稳定。
- 题目生成结果由服务端槽位覆盖分类、来源、维度和难度。
- 老题目补齐新增字段且保留现有答案、跳过状态和追问。

### 路由测试或纯函数边界测试

- 蓝图槽位不足时不覆盖旧题。
- 生成题数少于或多于蓝图槽位数时都拒绝保存。
- 成功生成后题目总数精确等于岗位配置。
- 跳过题仍被评分流程排除。

### 回归验证

- 全量 Vitest。
- TypeScript 类型检查。
- ESLint。
- 使用当前 Go 候选人的 JD/简历人工检查蓝图：必须包含 Go 基础、数据库/中间件、项目深挖、系统场景、沟通压力和 HR，不得出现简历未证明的实现事实。
